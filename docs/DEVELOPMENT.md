# 개발자 문서

구조, 설계상 결정, 성능 측정 기록입니다. 사용법은 [README](../README.md)를 보세요.

## 개발 환경

```bash
./run.sh --setup                      # 가상환경 생성 · 의존성 설치
~/.venvs/tactical-analysis/bin/python app.py [영상 | 프로젝트.fbproj]
```

- `tools/make_pitch_clip.py`, `tools/make_sample.py` 로 저작권 걱정 없는 합성 테스트 클립을 만들 수 있습니다.
- 미리보기와 내보내기는 `Project.render_output()` 한 경로를 공유하므로, 그래픽을 고칠 때는 내보낸 영상으로 확인하면 됩니다.

### 설계상 짚어둔 것

- **샷컷마다, 그리고 영상 하나를 분석하기 시작할 때마다 트래커를 리셋**합니다.
  `Analyzer` 는 프리셋별로 캐시돼 여러 영상에 재사용되는데(`전체 분석`이 대표
  사용처), 리셋하지 않으면 BoT-SORT 의 광류 기반 모션 보정이 이전 영상의 마지막
  프레임을 기준으로 새 영상 첫 프레임과 매칭을 시도하다가 값이 발산합니다. 실제로
  클립 3개를 연달아 분석했을 때 세 번째 클립에서 재현됐습니다.
- **전체 분석 큐는 오직 `finished` 신호에서만 다음 클립으로 넘어갑니다.** 분석
  스레드가 `done`/`failed` 신호 없이 조용히 죽는 경우(테스트 중 MPS 백엔드에서
  간헐적으로 재현됨)를 실제로 만났는데, 이때도 `finished` 는 반드시 옵니다.
  `done`/`failed` 핸들러는 결과만 기록하고 큐를 진행시키지 않으므로, 스레드가
  아무 신호도 없이 끝나도 배치가 멈추지 않고 그 클립을 실패로 기록한 뒤 계속
  진행합니다. 여기에 더해 3분 워치독을 둬 진짜 멈춘 경우도 건너뜁니다.
- 다만 트래커는 리셋 시 ID 카운터도 1로 되돌립니다. 그대로 두면 컷 전후의 서로
  다른 선수가 같은 ID로 합쳐지므로 **ID 오프셋**을 더해 전역적으로 유일하게 만듭니다
  (`Analyzer.run`).
- 짧은 끊김은 보간하되 **샷 경계를 넘어서는 보간하지 않습니다**. 넘기면 화면을
  가로지르는 유령 박스가 생깁니다.
- 대형선은 **라인을 사용자가 고정**하는 방식이라 경기장 호모그래피가 필요 없습니다.
  자동 분류라면 매 프레임 위치로 라인을 다시 추정해야 하고, 오버래핑한 풀백이
  미드필더로 재분류되며 선이 튑니다.
- 라인 안에서 선수를 잇는 순서는 **사용자가 클릭한 순서**를 따릅니다. 순서 정보가 없는
  예전 프로젝트에서만 발밑 좌표의 주성분(PCA)으로 정렬합니다. 중계 카메라에서는 화면
  x가 경기장 길이 방향, 화면 y가 좌우 방향에 대응하므로, "폭 방향으로 늘어선 라인"이
  화면에서는 세로로 나타납니다 — x로 단순 정렬하면 선이 꼬입니다.
- 표시 구간은 **목록**입니다. 같은 선수를 서로 떨어진 장면에서 각각 강조해야 하므로
  구간 하나로는 부족합니다(`PlayerState.spans`).
- 미리보기와 내보내기는 `Project.render()` 하나를 공유합니다. 두 경로가 갈라져
  "미리보기와 결과물이 다른" 문제를 막습니다.
- 링형에서 대형선은 발밑 중심이 아니라 **타원 경계까지의 거리를 계산해** 그 지점부터
  긋습니다(`_radius_along`). 중심까지 그으면 선이 링을 뚫고 들어가 지저분해집니다.
  두 링이 겹칠 만큼 가까우면 그 구간은 생략합니다.
- 정지 카드가 있으면 출력 길이가 원본과 달라지므로, 내보내기는 원본 프레임을 훑지 않고
  `Timeline.plan()` 이 만드는 (원본 프레임, 카드, 경과초) 순서를 따라갑니다. 정지 중에는
  같은 프레임을 반복해서 쓰므로 디코딩을 한 번만 합니다.
- 자막 크기는 픽셀이 아니라 **프레임 높이 대비 %** 로 잡습니다. 720p로 맞춘 자막이
  1080p에서 작아지는 문제를 막습니다.

## 추적 성능 튜닝 (실측)

실제 중계 클립 (1280×658, 301프레임, 화면당 평균 18.8명) 기준입니다.

| | 트랙 수 | 끝까지 유지 | 30f 미만 파편 | 속도 |
|---|---|---|---|---|
| 예전 (ByteTrack) | 53 | 9 | 21 | 21.0 fps |
| **지금 (BoT-SORT 튜닝 + 이어붙이기)** | **32** | **12** | **5** | 17.3 fps |

**파편이 76% 줄었습니다.** 탐지 수(18.8명/프레임)는 그대로이므로 순수하게 추적이
좋아진 것입니다. 속도는 18% 손해입니다.

무엇이 효과가 있었나:

1. **글로벌 모션 보정(`gmc_method: sparseOptFlow`)** — 가장 큰 효과. 중계 카메라가
   팬/줌 하면 화면 전체가 흐르는데, ByteTrack은 이를 보정하지 않아 가만히 선 선수도
   '움직인' 것으로 보고 매칭에 실패합니다.
2. **`track_buffer: 90`** — 놓친 트랙을 3초까지 살려둬 가림에서 회복합니다.
3. **`new_track_thresh: 0.4`** — 새 ID 생성을 까다롭게 해 파편을 줄입니다.
4. **조각 이어붙이기(`stitch_tracks`)** — 트래커가 놓쳐 새 ID로 되살아난 조각을,
   앞 트랙의 마지막 속도로 예측한 위치와 비교해 같은 선수면 합칩니다. 거리 문턱은
   박스 높이에 비례시킵니다(원근 보정). 샷 경계는 넘지 않습니다.

**ReID(외형 재식별)는 켰다가 다시 껐습니다.** 파편이 오히려 46개로 늘고 속도는
절반이 됐습니다. 같은 유니폼을 입은 선수끼리는 외형이 거의 구분되지 않아
도움이 되기는커녕 잘못된 매칭을 유발했습니다.

## 렌더 성능 (실측, Apple M2)

실제 중계 클립 (1280×658, 트랙 32개, 강조 10명) 기준. **출력은 픽셀 단위로 동일합니다.**

| 항목 | 이전 | 지금 |
|---|---|---|
| 설정 하나 바꿀 때 반응 | 68 ms | **8.7 ms** |
| 한 프레임 렌더 | 23.2 ms | **5.4 ms** |
| `stitch_tracks` (트랙 400개) | 6.37 s | **0.082 s** |

무엇을 고쳤나:

1. **현재 프레임 캐시** — 설정을 바꿀 때마다 같은 프레임을 다시 디코딩하고 있었습니다
   (46 ms). 뒤로 가는 seek 은 키프레임부터 다시 푸는 탓입니다. 이제 캐시에서 꺼내
   씁니다. 렌더는 항상 사본에 그리므로 캐시가 오염되지 않습니다.
2. **대형선 합성을 그린 영역으로 한정** — 선분 몇 개 때문에 화면 전체를 float32 로
   왕복하느라 17.7 ms 가 들었고, 이게 렌더 시간의 80% 였습니다. 좌표에서 경계 상자를
   바로 계산해 그 영역만 합성합니다(`np.nonzero` 로 찾으면 그 자체가 전체 스캔이라
   이득이 절반으로 줍니다).
3. **이름표 칩 캐시** — 칩 모양은 (글자, 크기, 색)에만 의존하고 위치만 매 프레임
   달라지는데 매번 다시 그리고 있었습니다.
4. **`stitch_tracks` 재구성** — 후보 쌍마다 `min()`/`max()` 전체 스캔과
   `sorted(boxes)[-4:]` 를 다시 하던 것을 트랙별 요약 사전계산으로 바꾸고, 후보를
   시간 창으로 잘라냈습니다(정렬 + `bisect`). 판정 로직은 그대로라 **병합 결과가
   박스 단위까지 동일**함을 옛 구현과 A/B 로 확인했습니다.

## 분석 성능 (Apple M2, MPS)

실제 중계 클립(1280×658, 207프레임, 라리가 중계)으로 측정한 값입니다.

| 프리셋 | 분석 속도 | 프레임당 탐지 | 150프레임 이상 유지된 트랙 |
|---|---|---|---|
| **빠름 (yolo11s · 960)** | **20.2 fps** | 15.6명 | 10개 |
| yolo11s · 1280 | 14.0 fps | 15.9명 | 11개 |
| 균형 (yolo11m · 1280) | 4.2 fps | 16.2명 | 11개 |
| 정밀 (yolo11x · 1280) | 1.3 fps | 16.5명 | 12개 |

**s → x 로 올려도 탐지 이득은 6% 남짓인데 속도는 15배 느려집니다.** 그래서 기본값을
`빠름`으로 두었습니다. 화면에 아주 작게 보이는 원거리 선수를 꼭 잡아야 할 때만
상위 프리셋을 쓰세요.

30초 클립(약 900프레임)은 빠름 프리셋에서 1분 이내입니다. 실시간 처리는 불가하며
오프라인 렌더 전용입니다.
